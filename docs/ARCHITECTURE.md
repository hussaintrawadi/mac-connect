# Architecture

Mac Connect is two native apps that speak one shared protocol. This document explains how
they're organised and how a message gets from one device to the other.

## Repository layout

```
.
├── AndroidApp/                 Kotlin app (Gradle, min SDK 26, target 35)
│   └── app/src/main/
│       ├── java/com/androidbridge/
│       │   ├── connection/     ConnectionManager, MessageTransport, PairingStore
│       │   ├── features/       one package per feature ("bridges")
│       │   ├── service/        foreground ConnectionService, BootReceiver
│       │   └── ui/             MainActivity, onboarding, pairing/QR scanner
│       ├── proto/messages.proto   (copy of the shared protocol)
│       └── res/                layouts, drawables, themes (iOS-style dark)
│
├── MacApp/                     Swift / SwiftUI app (XcodeGen, macOS 13+)
│   ├── project.yml             XcodeGen spec → generates AndroidBridge.xcodeproj
│   └── AndroidBridge/
│       ├── Sources/
│       │   ├── Connection/     ConnectionManager, PairingManager, MessageTransport
│       │   ├── Features/       one type per feature
│       │   ├── UI/             menu-bar popover, windows, onboarding
│       │   └── Generated/      messages.pb.swift (generated by protoc)
│       └── Resources/          Info.plist, entitlements
│
├── Shared/proto/messages.proto The single source of truth for the wire protocol
├── scripts/                    build_apk.sh, build_dmg.sh, gen_icon.py
└── docs/                       you are here
```

> The Mac side keeps a generated `messages.pb.swift` checked in, and the Android side
> generates Java from `proto/messages.proto` at build time via the protobuf Gradle plugin.
> `Shared/proto/messages.proto` is the canonical definition; the Android copy differs only
> in its Java options header. See [PROTOCOL.md](PROTOCOL.md).

## The connection lifecycle

### 1. Pairing (one time)

```
Mac (PairingManager)                         Android (PairingActivity / ScannerActivity)
────────────────────                         ───────────────────────────────────────────
opens NWListener on a fixed port (47291)
shows QR { v, id, ip, ips[], port }   ─────▶ scans QR with the custom CameraX/ZXing screen
accepts TCP connection               ◀─────  connects to ip:port
sends Mac info (id, public key, name) ─────▶ stores Mac id + key fingerprint
                                      ◀─────  sends phone info (id, public key, name)
saves paired device id + fingerprint         saves paired Mac id + fingerprint
```

After this, both sides remember each other; the QR is never needed again.

### 2. Discovery & connection

- The **Android** app runs a foreground `ConnectionService` that opens a `ServerSocket` on
  a port **derived from the Mac's device id** (a stable hash), and advertises itself over
  **mDNS** as `_androidbridge._tcp` with a name containing its own id.
- The **Mac** `ConnectionManager` browses mDNS for that service and connects.
- If mDNS is quiet (some routers drop it), the Mac falls back to **direct‑dialing the
  phone's last known IP** on the derived port. The Mac remembers the phone's IP on every
  successful connection.
- When Wi‑Fi changes, Android re‑registers its mDNS advertisement so the two re‑link
  automatically, like a Bluetooth device.

### 3. Transport

`MessageTransport` (both sides) frames each `Envelope` as a 4‑byte big‑endian length
followed by the serialized protobuf bytes, over one TCP socket. A heartbeat every 5s
detects dead connections and triggers reconnect with backoff.

## Message routing

Every payload is an `Envelope` with a `oneof`. Each side has a single switch that routes
the active field to the right component:

- **Mac:** `ConnectionManager.handle(_ envelope:)` → `case .smsConversation(let c): smsFeature.handle(c)` …
- **Android:** `ConnectionManager.handleMessage()` → `when (envelope.payloadCase) { SMS_SEND -> smsBridge… }`

A handy invariant: **every payload type that one side sends has a handler on the other
side.** When you add a message, add both the sender and the receiver.

## Feature components

Each feature is self‑contained and wired to the transport with an `onSendEnvelope`
callback. Rough mapping (Mac *Feature* ⇄ Android *Bridge*):

| Feature | Mac | Android |
|---|---|---|
| Screen mirror | `ScreenMirrorFeature` + `MirrorView` (VideoToolbox decode) | `ScreenMirrorBridge` (MediaProjection + MediaCodec), `TouchInjectionService` (AccessibilityService) |
| Calls / dialer | `CallFeature` + `CallHUDView` / `PhoneView` | `CallBridge`, `CallStateMonitor` |
| SMS | `SMSFeature` + `SMSView` | `SmsBridge`, `SmsReceiver` |
| Files | `FileSystemFeature` + `FileBrowserView` (Quick Look) | `FileSystemBridge` |
| Gallery | `GalleryFeature` + `GalleryView` | `GalleryBridge` (MediaStore) |
| Notifications | `NotificationFeature` (UserNotifications) | `BridgeNotificationListener` |
| Clipboard | `ClipboardFeature` (NSPasteboard) | `ClipboardBridge` (ClipboardManager) |
| Media control | `MediaControlFeature` | `MediaControlBridge` (MediaSessionManager) |
| Control the Mac | `MacSystemFeature` (volume/brightness/Wi‑Fi/Bluetooth/lock/sleep) | `MacBridge` (UI) |

## Key platform APIs

**macOS:** Network.framework (NWListener/NWBrowser/NWConnection), VideoToolbox,
AVFoundation, UserNotifications, IOKit.ps (battery), LocalAuthentication (Touch ID),
NSPasteboard, and private framework symbols via `dlopen` for brightness (DisplayServices /
CoreDisplay) and Bluetooth power (IOBluetooth).

**Android:** MediaProjection + MediaCodec (H.264), AccessibilityService (gesture & text
injection), MediaSessionManager, NotificationListenerService, ContentResolver
(SMS / contacts / call log / MediaStore), Network Service Discovery (NSD), TelecomManager,
and a foreground service for the persistent connection.
